Module 1 · Foundations

Classes, Objects & the Idea of OOP

Before writing a single class, it helps to understand the shift in thinking OOP asks for: instead of writing functions that act on data, you bundle data and the functions that act on it into one unit.

1.1 What is a class?

A class is a blueprint. It doesn't do anything by itself — it describes what an object (an instance of that class) will have and be able to do, once created.

Analogy A class is like a cookie cutter; an object is the cookie. The cutter defines the shape (attributes) and lets you press out cookies (instances), but the cutter itself is not edible. You can press out as many cookies as you like from one cutter, and each cookie can still be decorated (its own attribute values) differently.
# The blueprint (class) class Dog: def __init__(self, name, breed): self.name = name self.breed = breed def bark(self): return f"{self.name} says Woof!" # Creating objects (instances) from the blueprint rex = Dog("Rex", "Labrador") mia = Dog("Mia", "Poodle") print(rex.bark()) # Rex says Woof! print(mia.breed) # Poodle

__init__ is the constructor — Python calls it automatically when you create a new object, so you can set up that object's starting attributes.

Anatomy of a class, visually

1.2 self, and instance vs. class attributes

self refers to "this particular object." Inside a method, self.name means "the name belonging to whichever object called this method." Python passes it automatically — you never pass it manually when calling rex.bark().

Common misconception "self is a special Python keyword." It isn't — it's just a convention. You could name it anything, but every Python developer expects self, so deviating from it makes code harder to read.
Common misconception Confusing class attributes (shared by all instances, defined directly in the class body) with instance attributes (set per-object, usually via self.x = ... in __init__). Mutating a mutable class attribute (like a list) from one instance can silently affect every instance.
class Counter: total_created = 0 # class attribute — shared def __init__(self): Counter.total_created += 1 self.id = Counter.total_created # instance attribute a, b, c = Counter(), Counter(), Counter() print(a.id, b.id, c.id) # 1 2 3 print(Counter.total_created) # 3 — shared across all

Key takeaways

  • A class is a blueprint; an object is a concrete instance built from it.
  • __init__ runs automatically on creation to set up instance attributes.
  • self is a convention referring to the current instance, passed implicitly.
  • Class attributes are shared; instance attributes belong to one object.

Module 2 · Core Mechanics

Encapsulation & Building Real Classes

Now we go from "a class with data" to designing classes that protect their own integrity — the essence of encapsulation: bundling data with the logic that keeps it valid.

2.1 Why hide data?

Public attributes anyone can overwrite invite bugs. Python doesn't have true private variables, but it has strong conventions and tools to guide correct use.

Analogy Think of a vending machine. You interact through buttons (methods) — you never reach in and rearrange the coin mechanism (internal state) directly. The machine exposes a safe interface and hides the fragile internals.
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance # "_" = internal-use convention def deposit(self, amount): if amount <= 0: raise ValueError("Deposit must be positive") self._balance += amount def withdraw(self, amount): if amount > self._balance: raise ValueError("Insufficient funds") self._balance -= amount @property def balance(self): return self._balance # read-only view

A leading underscore (_balance) is a signal — "please don't touch this directly" — while a double leading underscore (__balance) triggers name mangling, making accidental access from subclasses harder (but never truly impossible).

Underscore conventions compared

Common misconception "Double underscore means truly private, like Java's private." It's actually name-mangling for collision avoidance, not access control — it can still be reached via obj._ClassName__name.

2.2 Properties: controlled access

The @property decorator lets a method be accessed like an attribute (account.balance instead of account.balance()), which keeps a clean interface while still running validation logic underneath.

acc = BankAccount("Asha", 100) acc.deposit(50) print(acc.balance) # 150 — reads like an attribute acc.withdraw(500) # raises ValueError: Insufficient funds

Key takeaways

  • Encapsulation bundles data with the logic that keeps it valid, hiding fragile internals.
  • Single underscore = convention; double underscore = name-mangling, not true privacy.
  • @property exposes controlled, attribute-like access to internal state.
  • Validate before mutating to keep an object always in a consistent state.

Module 3 · Practical Application

Inheritance & Composition

Inheritance lets a class reuse and extend another class's behavior. Composition builds objects out of other objects. Knowing when to reach for each is a core design skill.

3.1 Basic inheritance

class Animal: def __init__(self, name): self.name = name def speak(self): return f"{self.name} makes a sound" class Cat(Animal): # Cat inherits from Animal def speak(self): # override return f"{self.name} says Meow" class Fish(Animal): pass # inherits speak() unchanged print(Cat("Tom").speak()) # Tom says Meow print(Fish("Nemo").speak()) # Nemo makes a sound
Analogy Inheritance is like a family recipe passed down: a child class starts with everything the parent knows how to cook (methods), and can tweak individual recipes (override methods) or add brand-new dishes (new methods) without touching the original recipe book.

Class hierarchy diagram

3.2 super() and extending __init__

class Employee: def __init__(self, name, salary): self.name = name self.salary = salary class Manager(Employee): def __init__(self, name, salary, team_size): super().__init__(name, salary) # reuse the parent's setup self.team_size = team_size m = Manager("Priya", 90000, 6) print(m.name, m.team_size) # Priya 6

super() avoids duplicating the parent's setup logic. Without it, you'd have to copy-paste self.name = name into every subclass.

3.3 Inheritance vs. composition

Inheritance models "is-a" relationships (a Cat is an Animal). Composition models "has-a" relationships (a Car has an Engine). Overusing inheritance for convenience, rather than genuine "is-a" relationships, is one of the most common OOP design mistakes.

class Engine: def start(self): return "Engine roaring" class Car: def __init__(self): self.engine = Engine() # Car HAS an Engine (composition) def start(self): return self.engine.start()
RelationshipToolExample
"is-a"InheritanceCat is an Animal
"has-a"CompositionCar has an Engine
Common misconception "More inheritance layers = better design." Deep hierarchies are often a smell. If you catch yourself asking "does this really behave like its parent, or am I just reusing code?" — reach for composition instead.
Interactive exercise

Given this hierarchy, predict what each call prints, then reveal.

class Shape: def area(self): return 0 class Square(Shape): def __init__(self, side): self.side = side def area(self): return self.side ** 2 shapes = [Shape(), Square(4)] for s in shapes: print(s.area())
What prints? ▸
Output: 0 then 16. Each object uses its own area() — the base Shape returns 0, while Square overrides it. This loop is actually a preview of polymorphism, coming up in Module 4.

Key takeaways

  • Inheritance reuses and extends behavior for genuine "is-a" relationships.
  • super() calls the parent's implementation instead of duplicating it.
  • Composition ("has-a") is often a more flexible alternative to deep inheritance.
  • Overriding a method replaces the parent's version for that subclass only.

Module 4 · Mastery

Polymorphism, Abstraction & Dunder Methods

The final module ties everything together: writing classes that plug into Python's own syntax, and designing interfaces that many different classes can implement consistently.

4.1 Polymorphism

Polymorphism means objects of different classes can be used through the same interface, each responding in its own way — as you already saw with s.area() in Module 3.

Analogy Think of a universal remote's "power" button. Pressing it sends the same command to a TV, a soundbar, or a projector — each device (class) implements "power on" differently, but you interact with all of them the same way.
class Notifier: def send(self, msg): raise NotImplementedError class EmailNotifier(Notifier): def send(self, msg): return f"Emailing: {msg}" class SMSNotifier(Notifier): def send(self, msg): return f"Texting: {msg}" for n in [EmailNotifier(), SMSNotifier()]: print(n.send("Server down")) # Emailing: Server down # Texting: Server down

4.2 Abstraction with abc

Python's abc module lets you formally declare a class as abstract — it can never be instantiated directly, and forces subclasses to implement certain methods.

from abc import ABC, abstractmethod class Notifier(ABC): @abstractmethod def send(self, msg): ... Notifier() # TypeError: Can't instantiate abstract class
Common misconception "Polymorphism requires inheritance." Python also supports duck typing — "if it walks like a duck and quacks like a duck." Any object with a .send() method works in the loop above, whether or not it inherits from Notifier.

4.3 Dunder methods: integrating with Python itself

"Dunder" (double-underscore) methods let your class hook into built-in syntax like print(), +, len(), and comparisons.

class Vector: def __init__(self, x, y): self.x, self.y = x, y def __add__(self, other): return Vector(self.x + other.x, self.y + other.y) def __repr__(self): return f"Vector({self.x}, {self.y})" v = Vector(1, 2) + Vector(3, 4) print(v) # Vector(4, 6) — thanks to __repr__
Dunder methodHooks into
__init__Object creation
__repr__print() / debugging display
__add__The + operator
__len__len(obj)
__eq__The == operator
Common misconception Forgetting __repr__ and being confused by output like <__main__.Vector object at 0x7f...>. That's Python's default representation — define __repr__ to control it.
Final reasoning exercise

Given class Money: def __init__(self,a): self.a=a with only __init__ defined (no other dunders), what happens when you run print(Money(5))?

Reveal answer ▸
It prints something like <__main__.Money object at 0x...> — Python's default __repr__. To get a readable string, you must define __repr__ or __str__ yourself.

Key takeaways

  • Polymorphism lets different classes share a common interface with distinct behavior.
  • abc.ABC and @abstractmethod enforce that subclasses implement required methods.
  • Duck typing means Python cares about behavior, not declared type.
  • Dunder methods integrate custom classes into Python's built-in syntax and operators.

Final practical challenge

Design (on paper, in the sandbox below) a small class hierarchy for a library system:

  • An abstract base class LibraryItem with an abstract method checkout_info().
  • Two subclasses, Book and DVD, each implementing checkout_info() differently (e.g. different loan periods).
  • A __repr__ on each subclass so printing an item is readable.
  • A list holding both types, looped over polymorphically to print each item's checkout info.

Cheat sheet

class Name(ParentClass): # define + inherit class_attr = value # shared by all instances def __init__(self, arg): # constructor super().__init__() # reuse parent setup self.attr = arg # instance attribute @property def attr(self): ... # controlled read access def __repr__(self): ... # readable print() def __eq__(self, other): ... # == behavior

Summary notes

  • Class = blueprint, object = instance built from it.
  • Encapsulation: bundle data with validating logic; use _/__ conventions and @property.
  • Inheritance: reuse/extend via "is-a"; use super(); prefer composition for "has-a."
  • Polymorphism: shared interface, different implementations; supported by duck typing.
  • Abstraction: abc.ABC + @abstractmethod enforce a contract on subclasses.
  • Dunder methods integrate custom classes into Python's native syntax.
